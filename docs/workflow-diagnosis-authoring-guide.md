# 问题定位 Workflow 编写规范

## 1. 目的与适用范围

本文指导领域作者编写以故障或异常定位为目标的 Workflow。它规定如何拆解问题、说明步骤和建立证据闭环；除多次采集证据的引用规则外，不规定表达式语法、跳转配置、采集命令或具体业务内容。其他类型的 Workflow 可参考本文，但不受本文强制约束。

本文使用下列约束等级：

- **必须**：缺失会使流程无法被可靠理解、评审或执行。
- **应**：默认采用；偏离时应有明确的领域理由。
- **可**：按问题复杂度选择。

## 2. 拆解问题

Workflow 必须先说明待定位的现象、影响对象和已知边界，再将问题拆为可验证的局部假设。步骤应遵循“先证据、后归因”的主线：

1. 优先采集成本低、时效高且能区分多类原因的信息。
2. 根据结果排除或保留假设，并只为仍可能成立的假设补充采集。
3. 在证据足以支持时收敛到根因和修复建议。

作者不应按习惯罗列检查项，也不应让多个步骤重复采集不能改变后续判断的信息。遇到并列且互不依赖的假设时，可拆为并行分支；遇到共享前提时，应先验证该前提。

## 3. 说明判断步骤

每个判断步骤必须清楚说明以下四项：

1. **局部目标**：本步骤要缩小哪一部分不确定性，或验证哪个局部假设。
2. **采集信息**：为回答该问题需要哪些事实或数据。
3. **判断条件**：如何依据采集结果判定假设成立或不成立。
4. **结果去向**：两类判定分别继续排查什么，或收敛到哪个结论。

步骤名称和流程说明应反映其局部目标，而非只描述执行动作。一个步骤只应承担一个可独立判断的问题；当同一批信息服务于多个不同判断时，应明确各判断的使用范围和去向。

## 4. 描述证据与条件

采集信息必须说明采集对象或来源、它要回答的问题、输出信息的含义，以及该信息可用于支持或排除哪些假设。作者应区分事实、推断和未知项；未采集或可信度不足的信息不能作为结论依据。

判断条件必须说明比较或观察的对象、条件成立与不成立各自的业务含义，以及各自对应的后续排查或结论。条件应能被已有输入或本步骤采集结果验证，且应避免使用“异常”“正常”等没有判定边界的描述。存在阈值、时间窗口或适用前提时，应在流程说明中交代其领域含义和适用范围。

## 5. 分支与结论闭环

每条分支必须减少不确定性：要么排除一组假设，要么进入验证更具体假设的步骤，要么基于充分证据收敛结论。分支不应回到已完成且不产生新增证据的步骤。

结论必须由前序步骤的可追溯证据支持，并说明其适用条件和建议的后续处置。未验证的假设不得直接作为终点结论；证据不足时，应继续采集、标记为待确认，或明确流程的适用边界。

## 6. 引用多次采集结果

同一命令执行多次时，每次结果都是独立证据。作者必须在条件表达式中明确选择结果下标，例如 `outputs.status[0].version`；不得用 `outputs.status.version` 隐式代表任意一次或最后一次结果。下标从 0 开始，也可使用对应的 Python 负数下标、动态整数或切片。使用动态下标或切片时，步骤说明应交代选择规则及其业务含义。

多次采集的调用 Key 必须是合法 Python 标识符，并在整个 Workflow 内唯一。历史表达式缺少下标时会显示 warning，作者应根据证据含义人工修正；系统不会自动选择采集结果。

## 7. 作者自检

- 是否明确了现象、影响范围和本流程不覆盖的边界？
- 每个步骤是否都有局部目标、采集信息、判断条件和结果去向？
- 每项采集信息是否能改变后续判断，且说明了含义与适用范围？
- 每个条件的成立与不成立是否都有清楚的业务含义和下一步？
- 每个结论是否能回溯到足以支持它的证据链？
- 多次采集条件是否明确引用了所需结果下标，并说明动态选择规则？
